# 基于 Yuxi 的飞书企业知识平台集成设计

**状态：** 已于 2026-08-12 在对话中分段确认通过

**基线：** Yuxi `v0.7.1`

**部署边界：** 单一企业、单一飞书租户、私有化部署

**目标飞书根节点：** `POFEwqvUaiwFBXkNRuScMy3inkd`

**目标链接：** <https://quickdone.feishu.cn/wiki/POFEwqvUaiwFBXkNRuScMy3inkd>

## 1. 文档效力

本文档定义 Knowledge Platform V1 从本地原型迁移为正式技术底座的目标设计，覆盖 Yuxi 集成、飞书 Wiki 同步、权限继承、知识加工、人工审核、正式发布、RAG 问答、临时任务资料、可靠任务和验收边界。

本文档取代旧设计中以下已经失效的约定：

- 不再使用飞书多维表格作为业务仓库、审核工作台或会话存储。
- 不再将 Fastify、本地 JSON、确定性 AI 和本地词法检索作为正式实现。
- 不再将飞书 Bitable 视为未来 Business Repository。
- 不让原始飞书资料或普通文档 Chunk 直接成为正式企业知识。

旧设计仍可用于理解当前原型的产品原则和历史决策，但与本文档冲突时以本文档为准。

## 2. 目标与完成范围

第一阶段建设一套可在本机隔离部署、可接入真实企业飞书、可形成正式知识并支持有依据问答的系统，跑通四条闭环：

1. 飞书受控目录中的资料被递归同步、解析并保留不可变证据版本。
2. AI 从证据中提出原子候选，人工审核后发布为正式知识。
3. 普通员工仅使用有权限、已审核且索引成功的正式知识进行问答。
4. 用户可上传当前任务资料，例如客户需求书，并结合企业正式知识生成逐条响应。

第一阶段必须使用真实飞书根节点完成只读验收，但不得回写、移动或删除飞书原文。

## 3. 核心原则

1. **PostgreSQL 是唯一业务真相。** Redis、Milvus 和缓存不能保存不可替代的业务状态。
2. **飞书是原始证据源。** 原始资料进入加工流水线，不因位于受控目录就自动成为正式知识。
3. **AI 提议，人工决定。** AI 可以解析、提取、比较、分类和建议，不能发布或改写正式知识。
4. **正式知识与 RAG Chunk 分离。** 正式知识面向治理、版本和审计；RAG 表示面向召回，可以重建。
5. **权限默认拒绝。** 无法确认当前飞书权限时，不召回正文，也不打开引用。
6. **来源变化不覆盖历史。** 资料、知识和审核均保留不可变历史版本。
7. **临时资料是任务输入，不是企业事实。** 当前对话资料可以参与分析，但不能自动沉淀为企业知识。
8. **普通用户只看到业务概念。** 不向普通员工暴露 Chunk、Embedding、Top-K、提示词、图谱或模型路由等运行细节。
9. **先完成最小闭环。** 第一阶段不引入音视频 ASR、知识图谱、多企业租户、本地大模型和自动文档排版。

## 4. 选型结论

采用“基于 Yuxi 扩展统一后端”的方案：

```text
现有 React 中文业务界面
            |
            v
定制后的 Yuxi FastAPI
  |-- 飞书登录与身份映射
  |-- 飞书 Wiki 同步
  |-- Asset / Candidate / Review / Knowledge 治理
  |-- Yuxi 文档解析与 OCR
  |-- Yuxi RAG / Agent
  `-- 权限校验与引用服务
            |
            +-- PostgreSQL：唯一业务主库
            +-- MinIO：原文件和解析产物
            +-- Milvus：可重建检索索引
            `-- Redis：投递、缓存和流式事件
```

不采用以下方案：

- 不让 Fastify 治理系统和 Yuxi 长期作为两个业务服务并列运行。
- 不把 Yuxi 的解析、RAG 和 Agent 代码逐块移植到 TypeScript 工程。
- 不通过 iframe 嵌入整个 Yuxi，也不让普通用户在两套产品界面之间切换。

实施约束：

- 在同级独立目录和独立 Docker 资源中部署 Yuxi，不覆盖当前工程。
- 固定使用 `v0.7.1`，不直接以变化中的 `main` 为生产基线。
- 保留 Yuxi 上游地址，只选择性合并安全和稳定性修复。
- 新系统验收完成前，不删除当前工程、数据或恢复点。
- 当前 JSON 演示数据不迁入正式数据库，只保留为测试样例。

## 6. 用户、角色与登录

系统面向四种身份：

| 身份 | 主要能力 |
| --- | --- |
| Employee | 知识问答、上传当前任务资料、查看有权引用、提交反馈 |
| Knowledge Owner | Employee 能力，加工资料、处理分配给自己的审核任务、管理自己负责的正式知识 |
| Admin | 管理同步、任务、负责人、来源权威、系统状态和全部治理元数据 |
| Local Superadmin | 部署维护、模型与基础设施配置、飞书登录故障应急 |

登录规则：

- Employee、Knowledge Owner 和 Admin 统一使用飞书授权登录。
- 系统保存飞书用户标识、部门映射和 OAuth 状态。
- 保留一个本地应急超级管理员账号。
- 本地超级管理员可以维护系统，但默认不能绕过飞书 ACL 查看无权访问的知识正文。
- 角色权限决定能否执行治理动作；飞书 ACL 决定能否读取具体知识内容。两者不能混用。

## 7. 数据所有权与存储

| 数据 | 唯一正式存储 |
| --- | --- |
| 飞书节点映射、同步游标、权限快照 | PostgreSQL |
| Asset、Candidate、Review、Knowledge | PostgreSQL |
| AssetRevision、KnowledgeVersion | PostgreSQL 元数据 + MinIO 正文快照 |
| 原文件、Markdown、OCR 结果 | MinIO |
| 正式知识和临时资料检索表示 | Milvus，严格分区 |
| 任务事实状态和 Outbox | PostgreSQL |
| 任务投递、流式事件和缓存 | Redis |
| 原始业务资料 | 企业飞书 |
| 多维表格 | 不使用 |

Milvus、Redis 数据丢失后必须能够根据 PostgreSQL 和 MinIO 重建。PostgreSQL 不可用时停止业务写入，不降级回本地 JSON。

## 8. 领域模型

### 8.1 Asset 与 AssetRevision

`Asset` 表示一个稳定的外部资料对象，不表示某次内容快照。

核心字段：

- 稳定业务 ID
- `provider=FEISHU_WIKI`
- Wiki `node_token` 和实际对象 `obj_token/obj_type`
- 父节点、完整目录路径、标题和原文链接
- 负责人、来源权威等级和当前处理状态
- 当前 Revision 引用
- 是否仍在受控根目录内
- 当前删除、移出或访问状态

`AssetRevision` 表示资料的一次不可变内容版本：

- 来源修改时间、内容哈希和同步时间
- 原始文件或导出文件位置
- 解析后 Markdown 或结构化正文位置
- 解析方法、配置和处理结果
- 原文块、页码、表格或段落定位信息
- 本次 Revision 对应的 ACL 快照

新内容创建新 Revision，不覆盖旧证据。

受控根目录开始首次同步前，Admin 必须显式配置一个默认 Knowledge Owner 和默认 Authority。新 Asset 继承根目录配置；后续可以人工调整单个 Asset 的负责人和 Authority，但 AI 无权创建、提高或修改 Authority。第一阶段不增加按子目录自动分配负责人的规则，避免引入无法解释的隐式优先级。

### 8.2 Section

`Section` 是从一个 AssetRevision 解析出的证据片段：

- 章节标题和原文内容
- 飞书块 ID、页码、表格或段落位置
- 解析正文中的字符或 Token 范围
- 来源 Revision 和内容哈希

Section 是候选提取的证据，不是正式知识，不能直接进入普通员工问答。

### 8.3 Candidate

`Candidate` 是 AI 从证据中提出的一条原子知识候选。合格形式为：

```text
主体 + 条件/适用范围 + 结论 + 生效约束
```

例如：

> Q900 3.2 版本在标准部署模式下，最低需要 6 张 A800。

每条 Candidate 保存：

- 标题、规范化内容和知识类型
- 主体、条件、结论和生效约束
- 来源 AssetRevision、Section、定位和原文摘录
- 来源权威等级、AI 置信度和比较关系
- 比较目标、AI 理由、模型版本和提示版本
- 候选哈希、状态、创建及审核时间

同一 Revision、同一位置和同一规范化内容重复加工时，不重复创建 Candidate。

### 8.4 Review

`Review` 是不可变的人工作业和知识变更记录。支持：

- 新增知识
- 更新已有知识
- 冲突处理
- 失效或归档复核
- 用户反馈修复
- 来源变化复核

审核任务保存候选、当前快照、建议内容、差异、风险、负责人、最终决策、最终内容、审核意见和时间。已完成 Review 不允许重新编辑；纠错必须创建新的复核任务。

### 8.5 Knowledge 与 KnowledgeVersion

`Knowledge` 表示逻辑上稳定的企业事实：

- 稳定知识 ID
- 当前发布版本
- 当前状态、负责人、分类和标签
- 是否允许 AI 使用

`KnowledgeVersion` 是不可变的正式版本快照：

- 完整正式内容、版本号和适用条件
- 生效、失效时间和状态
- 主来源、辅助来源及其 Revision/Section
- 审核任务、审核人和审核意见
- 审核时 ACL 快照，仅用于审计
- 索引状态、索引模型和索引版本

运行时访问使用来源的**当前 ACL**，不能把历史 ACL 快照当作持续授权。

### 8.6 Job 与 Outbox

关键后台任务均保存为 PostgreSQL Job：

- 稳定任务 ID、类型和业务对象 ID
- 幂等键、阶段、状态和进度
- 尝试次数、错误代码、下次重试时间
- 执行配置版本和时间信息

业务事务通过 Outbox 记录待投递事件；Redis/ARQ 只负责执行投递和事件分发。

### 8.7 Conversation 与 SessionAsset

`Conversation` 保存对话元数据和消息。`SessionAsset` 表示当前对话临时资料：

- 绑定上传用户和对话 ID
- 原文件、解析正文和会话级检索表示
- 默认 24 小时有效期
- 当前处理状态和删除状态

SessionAsset 不是 Asset，不产生企业候选，不进入正式知识索引。

## 9. 飞书 Wiki 同步

### 9.1 根目录与只读边界

系统仅扫描指定 Wiki 根节点及其全部后代节点。第一阶段申请和使用读取权限，不修改、移动或删除飞书原文。

### 9.2 同步策略

```text
首次手动全量扫描
      |
      v
飞书事件通知触发增量同步
      |
      v
每日一次完整目录对账
      |
      v
管理员可随时执行“立即同步”
```

同步能力必须支持递归、分页、限流、自动重试、断点续传和幂等。单个文件失败不得阻塞其他文件。每次运行显示发现、新增、更新、删除、失败和跳过数量。

### 9.3 变更处理

| 飞书变化 | 系统行为 |
| --- | --- |
| 新增节点 | 创建 Asset 和首个 Revision，进入加工 |
| 修改正文 | 创建新 Revision，重新提取和比较候选 |
| 仅重命名 | 更新标题和路径，不重复解析正文 |
| 根目录内部移动 | 更新路径，不新建 Asset |
| 移出受控根目录 | 标记移出，立即停止相关正式知识召回 |
| 删除节点 | 标记删除并停止召回，不物理删除历史 |
| 恢复节点 | 创建或恢复新 Revision，重新加工 |
| 权限变化 | 更新 ACL 快照并立即重新计算可见范围 |

飞书暂时不可用时保留上次游标并重试，不能把“无法确认”误判为节点删除。

### 9.4 内容范围

第一阶段处理：

- 飞书 Wiki 页面和新版文档
- PDF、Word、PowerPoint、Excel
- Markdown、TXT
- 图片及 OCR
- 已形成文字的会议纪要

复杂多维表格、无法导出的特殊对象和其他暂不支持对象仍创建 Asset，并显示“暂不支持”原因。音视频记录为“等待第二阶段处理”，不进入正式加工。

## 10. 飞书 ACL 继承

### 10.1 权限快照

系统将飞书资源权限规范化为 `SourceAclSnapshot`、ACL 绑定和可检索访问策略：

- 指定用户
- 指定部门
- 知识库成员范围
- 企业公开范围
- 来源权限版本和同步时间

PostgreSQL 根据来源当前 ACL、组织成员关系和多来源交集生成规范化 `AccessPolicy`。语义相同的策略复用同一个稳定策略 ID；每个可检索 KnowledgeVersion 只引用一个当前有效策略 ID。ACL 或组织成员关系变化时，先让旧策略失效，再通过高优先级 Outbox 重新计算访问投影和更新索引元数据。

权限数据是业务授权依据，不是来源权威等级。Authority 只描述证据可靠程度，不能用于访问判断。

### 10.2 检索与引用校验

执行两层权限控制：

1. 检索前由 PostgreSQL 权限服务计算当前用户可用的策略 ID，Milvus 只在这些策略 ID 内召回；模型看不到被排除的内容。
2. 用户打开引用时再次校验当前飞书身份和最新权限。

PostgreSQL 是权限判定的唯一事实来源，Milvus 中的策略 ID 只是可重建过滤投影。权限服务不可用、投影版本落后或策略更新尚未完成时，相关知识默认不参与召回。这样既避免先召回无权正文再过滤，也避免无权结果占满 Top-K 导致有权知识无法进入候选集。

以下情况一律默认拒绝：

- ACL 同步失败或状态无法确认
- 飞书明确返回无权限
- 来源已删除或移出受控目录
- 用户 OAuth 身份无法与飞书用户可靠映射

本地超级管理员不能绕过以上规则。历史会话重新打开时也重新校验当前权限。

### 10.3 多来源知识

一条 KnowledgeVersion 使用多个证据来源时，运行时可见范围为这些来源**当前 ACL 的交集**。用户必须能够访问该版本采用的全部证据来源。

审核时 ACL 快照用于证明当时的授权状态；当前召回和引用始终使用最新 ACL。

## 11. 知识加工流水线

每个 AssetRevision 的处理状态：

```text
DISCOVERED
  -> FETCHING
  -> PARSING
  -> EXTRACTING
  -> COMPARING
  -> READY
```

任一步骤失败进入 `FAILED`，保存失败阶段、错误原因、已完成步骤、重试次数、下次重试时间和执行配置。重试从最近安全阶段继续。

### 11.1 候选提取约束

AI 不能输出：

- 整篇文档或完整章节作为一条候选
- 脱离上下文的词语或数字碎片
- 没有直接原文证据的推测
- 仅依赖模型常识的企业结论

模型输出必须通过结构 Schema 校验。一次调用最多执行三次尝试；仍然无效时创建加工异常，不静默接受结果。

### 11.2 正式知识比较

候选关系：

| 关系 | 含义 | 处理 |
| --- | --- | --- |
| NEW | 没有相关正式知识 | 新增审核 |
| DUPLICATE | 语义和约束一致 | 置信度不低于 0.90 时自动关闭，否则人工确认 |
| UPDATE | 同一事实的新版本或补充 | 更新审核并显示差异 |
| CONFLICT | 相同条件下结论互斥 | 高风险冲突审核 |
| INSUFFICIENT | 证据或上下文不足 | 进入待补充列表，不直接发布 |

比较顺序：

1. 按主体、版本、类型和适用条件缩小范围。
2. 使用正式知识混合检索召回相关项。
3. 大模型输出结构化比较和理由。
4. 确定性规则检查数值、版本、否定词和适用条件。
5. 低置信度、无效结构或无法判定时交给人工。

## 12. 审核与正式发布

### 12.1 审核界面

审核人员看到：

- 候选知识和原文摘录
- 飞书原文定位与打开链接
- 当前正式知识和差异
- 来源权威程度
- AI 判断、理由和置信度
- 受影响的知识和问答范围
- 历史审核记录

允许动作：

- 修改后创建新知识
- 修改后更新已有知识
- 保留当前知识
- 判为重复
- 驳回候选
- 标记证据不足
- 归档已有知识
- 转交给对来源有访问权的其他负责人

每次完成审核必须填写意见。

### 12.2 状态

Knowledge 发布状态：

```text
DRAFT
PUBLISHING
ACTIVE
STALE
ARCHIVED
```

索引状态：

```text
PENDING
INDEXED
FAILED
```

只有同时满足以下条件的 KnowledgeVersion 才能进入普通问答：

```text
Knowledge.status = ACTIVE
Knowledge.ai_enabled = true
KnowledgeVersion.index_status = INDEXED
所有来源仍在受控范围且可验证
当前用户满足所有来源 ACL
```

### 12.3 发布一致性

```text
审核通过
  |
  v
同一 PostgreSQL 事务：
  创建 KnowledgeVersion
  更新待发布指针
  写入索引 Outbox
  |
  v
Worker 构建正式知识 RAG 表示并写入 Milvus
  |
  +-- 成功：原子切换为 ACTIVE / INDEXED
  `-- 失败：保持 PUBLISHING / FAILED，进入重试
```

新版本索引成功前，旧 ACTIVE 版本可以继续回答，前提是旧版本来源仍存在、仍在受控目录内且当前 ACL 有效。来源正文变化会产生复核任务，但不会在人工审核前自动改写旧正式版本。

若来源被删除、移出目录、明确撤权或证据文件丢失，则旧版本也必须立即停止召回，不能为了可用性继续使用失效证据。

## 13. RAG 索引设计

正式知识与临时资料使用严格隔离的检索空间：

- `formal_knowledge`：仅保存已发布 KnowledgeVersion 的可重建检索表示。
- `session_documents`：仅保存当前对话临时资料，带用户、对话和过期时间过滤。

原始 Asset Section 不进入普通员工检索。候选比较直接处理当前 Revision，并只召回正式知识作为比较目标。

一条 KnowledgeVersion 可以生成多个 RAG 表示，例如标题、原子陈述、同义问题和适用条件组合，但它们都引用同一正式版本和证据链。

Embedding 模型一旦用于正式索引，切换模型必须建立新索引版本并全量重建，不能在同一索引混用不同向量空间。

第一阶段使用 Milvus 向量与 BM25 混合召回，不强制配置独立 Rerank 模型。只有评估证明需要时再增加。

## 14. 知识问答

### 14.1 普通企业知识问答

系统仅检索当前用户有权访问的正式知识，生成回答并返回：

- 回答正文
- `SUPPORTED`、`INSUFFICIENT` 或 `CONFLICTING` 结论状态
- 使用的 KnowledgeVersion
- 正式知识详情引用
- 对应飞书原文引用

没有充分正式依据时明确回答“暂无足够可靠资料”，不能用模型常识补成企业承诺。

### 14.2 当前任务资料联合推理

用户上传的需求书、招标文件、技术规格、客户问题清单或项目背景既是引用来源，也是当前任务输入。

```text
用户任务指令
      +
当前对话临时资料
      +
当前用户有权访问的企业正式知识
      |
      v
识别需求和约束
      |
      v
拆分为可追踪条款
      |
      v
逐条检索正式知识
      |
      v
满足 / 部分满足 / 不满足 / 依据不足
      |
      v
生成响应内容和双来源引用
```

例如客户文件要求兼容某数据库，这只能证明客户提出该要求，不能证明公司已经具备该能力。只有正式知识可以作为企业能力依据。

### 14.3 使用范围

界面提供三种业务范围：

| 范围 | 参与推理内容 |
| --- | --- |
| 仅企业知识 | 当前用户有权访问的正式知识 |
| 仅当前资料 | 用户问题和当前对话资料 |
| 企业知识＋当前资料 | 当前资料作为任务输入，并检索正式知识 |

上传任务资料后默认选择“企业知识＋当前资料”。

### 14.4 双来源引用

回答必须区分：

- **需求来源：** 当前对话临时资料的页码、章节或段落。
- **企业依据：** 正式 KnowledgeVersion 及飞书来源。

打开企业依据时重新执行飞书 ACL 校验；打开需求来源时校验当前用户和对话归属。

### 14.5 临时资料生命周期

- 原文件、解析正文和临时索引默认 24 小时后删除。
- 用户可以提前删除，删除后立即停止参与生成。
- 对话消息和已生成响应可以保留，但过期附件不能再次打开或参与推理。
- 临时资料不得被其他用户、其他对话或企业正式检索召回。
- 用户希望将临时资料沉淀为企业知识时，必须主动提交给负责人并重新走完整治理流程。

### 14.6 附件安全

上传文件属于不可信输入。附件中的文字不能修改系统规则、触发未授权工具或绕过飞书权限。

系统必须隔离任务指令、临时资料和正式知识，拒绝宏和脚本执行，检查文件名、压缩包和嵌入链接，并确保模型输出不泄露未授权检索结果。

## 15. 反馈修复闭环

用户可标记：

- 回答错误
- 内容过期
- 缺少信息
- 引用错误
- 需求理解错误
- 其他

处理规则：

- 指向企业正式知识的问题创建对应负责人的知识复核任务。
- 仅涉及临时资料理解的问题记录为对话反馈，不污染企业知识。
- 无法分类的问题进入管理员待分类列表。
- 修复知识后不修改历史回答；历史回答继续记录当时使用的知识版本。

## 16. 模型和解析服务

第一阶段使用外部兼容 OpenAI 接口的模型服务，本机不部署大模型。

至少配置：

- 一个支持中文、长上下文和结构化输出的对话模型，用于问答、候选提取和知识比较。
- 一个中英文 Embedding 模型。

模型、提示和结构 Schema 分别版本化。模型不可用时，飞书同步和原文保存可以继续，候选提取、比较或问答进入等待或失败状态。

本机第一阶段启用普通文档解析和 RapidOCR，不启动 MinerU GPU、PaddleX GPU 或本地推理服务。

所有模型密钥、飞书应用密钥和 OAuth 密钥只写入不提交 Git 的本机私有配置，不发送到聊天，不写入普通日志。

## 17. 可靠任务与故障处理

飞书扫描、下载、解析、OCR、候选提取、索引发布和权限撤销均使用持久 Job + Outbox + Redis/ARQ Worker。

可靠性规则：

- PostgreSQL 保存任务最终事实，Redis 不保存唯一状态。
- API 或 Worker 重启后，未完成任务能够重新派发。
- 每个阶段均有幂等键，重复执行不重复创建业务对象。
- 飞书限流、网络和临时基础设施错误使用指数退避，默认最多五次自动尝试。
- 达到上限后进入“需要人工处理”，不无限重试。
- 权限撤销和来源删除任务优先于普通解析任务。
- 管理员可以查看、筛选、重试和取消任务；取消不删除已形成的证据和历史。

| 故障 | 系统行为 |
| --- | --- |
| 飞书暂时不可用 | 保留游标并延迟重试，不误判删除 |
| 飞书明确无权限 | 立即停止相关内容召回并记录异常 |
| 文件下载失败 | 保留 Asset，Revision 标记失败并支持单独重试 |
| OCR 或解析失败 | 不生成候选，显示具体失败阶段 |
| 模型不可用 | 保存已有解析结果，后续重试 |
| 模型结构无效 | Schema 校验和有限重试，之后转加工异常 |
| Milvus 写入失败 | 新版本保持 PUBLISHING，旧有效版本继续使用 |
| PostgreSQL 不可用 | 停止写入，不降级为 JSON |
| Redis 不可用 | Outbox 保留，恢复后重新投递 |
| MinIO 证据丢失 | 标记证据不完整、停止相关新召回并创建复核 |
| ACL 无法确认 | 默认拒绝，不沿用可能过期的宽松权限 |

## 18. API 边界

React 只访问统一 FastAPI。核心产品接口按以下资源边界组织：

```text
/api/auth/feishu/*              飞书登录、回调和会话
/api/governance/sources/*       飞书根节点、同步运行和 ACL 状态
/api/governance/jobs/*          任务列表、详情、重试和取消
/api/governance/assets/*        资料、Revision、Section 和重新加工
/api/governance/candidates/*    候选列表和详情
/api/governance/reviews/*       审核列表、详情、转交和完成
/api/governance/knowledge/*     正式知识、版本、更新和重建索引
/api/chat/conversations/*       对话、消息、临时资料和反馈
/api/citations/*                引用解析和实时权限校验
```

Yuxi 原有 AgentRun、SSE、模型、OCR 和知识库内部接口可由上述用例层复用，但普通业务组件不直接拼装基础设施接口。

## 19. 前端信息架构

保留当前 React 中文界面和浅蓝色视觉方向：

- Employee 主要进入知识问答。
- Knowledge Owner 看到资料、候选、审核和正式知识。
- Admin 额外看到同步、失败任务、权限异常和系统状态。
- Yuxi Vue 页面只供技术管理员配置模型、OCR 和诊断基础设施，不作为普通入口。

问答输入框保持固定在页面底部。需求来源和企业依据使用不同视觉标签。技术参数不出现在普通用户界面。

## 20. 本机基线部署验收

开始定制前，原版 Yuxi `v0.7.1` 必须在隔离环境中通过：

1. 管理员登录。
2. 外部大模型调用。
3. 文本、PDF 和图片上传与解析。
4. 文档写入 Milvus 并完成检索。
5. Agent 根据测试文档回答并返回来源。
6. 容器重启后数据库和文件仍存在。

第一阶段部署：

- FastAPI
- Yuxi Worker
- PostgreSQL
- Redis
- MinIO
- Milvus 和 etcd
- RapidOCR 或普通文档解析
- Yuxi 技术管理界面

第一阶段不部署 Neo4j、GPU 解析服务、本地大模型、Kubernetes 或高可用集群。

## 21. 测试设计

### 21.1 领域测试

- Candidate 关系与审核动作矩阵
- 正式知识状态迁移和版本不可变
- 来源权威不能被 AI 提高
- 未发布知识不能回答
- 来源失效后停止召回
- 多来源 ACL 交集

### 21.2 飞书连接测试

- 分页、递归、重复节点和幂等扫描
- 新增、更新、移动、删除和恢复
- 限流、超时和令牌过期
- webhook 重复、乱序和遗漏
- 中断后从游标继续
- 1000 节点模拟目录扫描

真实企业飞书根节点只执行只读验收，测试产物不得保存真实正文和凭证。

### 21.3 集成测试

- 审核发布和 Outbox 的事务一致性
- Worker 失败和重启恢复
- 索引失败和重试
- 新版本索引成功后的原子切换
- Redis 清空后根据 PostgreSQL 重新投递
- Milvus 删除后根据正式版本重建索引

### 21.4 权限与安全测试

- 用户、部门、共享范围和权限交集
- 飞书撤权后的立即阻断
- 历史引用实时校验
- 本地超级管理员不能绕过 ACL
- 临时附件跨用户和跨对话访问
- 附件提示注入、恶意文件名和非法压缩包
- 日志与接口不泄露凭证或无权正文

### 21.5 端到端业务测试

**Q900 知识更新：**

```text
4 张 A800 原文
  -> 同步
  -> 候选
  -> 审核发布 V1
  -> 问答返回 4 张
  -> 飞书改为 6 张
  -> 生成 UPDATE
  -> 审核前仍使用旧有效版本
  -> 审核发布 V2
  -> 问答返回 6 张并引用新原文
```

**客户需求响应：**

```text
上传需求书
  -> 提取需求条款
  -> 逐条检索正式知识
  -> 输出满足 / 部分满足 / 不满足 / 依据不足
  -> 同时引用需求文件和企业知识
  -> 临时文件过期后停止访问和参与推理
```

### 21.6 浏览器验收

- 飞书登录
- 固定底部输入框
- 上传、解析进度和失败提示
- 双来源引用
- 审核差异与决策
- 同步和失败任务查看
- 桌面端与移动端关键操作

## 22. 分阶段实施

1. **Yuxi 基线部署**：完成模型、解析、检索、Agent 和重启验证。
2. **治理后端**：建立 PostgreSQL 领域模型、不可变版本、可靠任务和 FastAPI 接口。
3. **飞书接入与权限**：完成飞书登录、Wiki 递归同步、Revision、ACL 和撤权阻断。
4. **知识加工与发布**：完成候选、比较、审核、Outbox 发布和正式索引。
5. **问答与临时资料**：接入 React，完成联合推理、双来源引用和反馈闭环。
6. **整体加固与切换**：完成真实目录、安全、故障恢复、备份和旧 Fastify 停用。

每个里程碑必须独立验收，未通过不得进入下一阶段。

## 23. 第一阶段不包含

- 音视频 ASR 和说话人识别
- Neo4j 知识图谱
- 多企业 SaaS 租户
- 飞书多维表格
- 本地大模型
- 自动修改或删除飞书原文
- 自动发布正式知识
- 使用附件内容证明未经正式知识确认的产品能力
- 自动生成正式 Word、PDF 或投标文件
- Kubernetes、高可用和多节点生产部署
- 向业务用户开放复杂 Rerank 和检索参数

## 24. 最终验收标准

只有同时满足以下条件，第一阶段才算完成：

1. Yuxi `v0.7.1` 在本机隔离部署并通过基础验证。
2. 当前 React 界面已接入统一 FastAPI 后端。
3. PostgreSQL 成为唯一业务主库，Fastify 和 JSON 不再承担正式业务。
4. 指定飞书 Wiki 根节点能够递归、增量、幂等同步。
5. 飞书权限继承、撤权和引用校验真实有效。
6. 原始资料不能绕过人工审核进入普通问答。
7. 正式知识版本不可变、可追溯、可重新索引。
8. Q900 从 4 张更新到 6 张的场景端到端通过。
9. 上传客户需求并结合正式知识生成响应的场景通过。
10. 关键任务在重启后可恢复，索引失败不暴露半成品。
11. 自动测试、真实飞书只读验收和浏览器验收全部通过。
12. 旧工程在明确确认切换前保持可恢复，不擅自删除。
